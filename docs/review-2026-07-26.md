## 1. Ringkasan Kondisi

| Aspek | Nilai | Catatan |
|---|---|---|
| Arsitektur | Kuat | Server Actions + RPC `security definer`, service-role tidak pernah bocor ke klien |

Ini codebase yang rapi. Masalah yang tersisa bukan soal kualitas kode — tapi soal
**alur pembayaran yang belum tersambung ke database** dan **biaya variabel AI yang tak dibatasi**.

## 2. Temuan — Wajib Diperbaiki

### 2.1 `main` merah — test gagal
`App/tests/menu-table-inventory.test.ts` gagal 2 test.

```
No "getCafeBySlug" export is defined on the "@/lib/analytics" mock
```

Penyebab: commit `cb284d4` (dedupe `getCafeBySlug` pakai React `cache()`) menambah
impor `getCafeBySlug` dari `@/lib/analytics`, tapi mock di test hanya meng-ekspor
`getOwnerCafeSlug`. Perbaikan: tambahkan `getCafeBySlug: mocks.getCafeBySlug` di
`vi.mock("@/lib/analytics", ...)` baris 23.

Perbaikan sepele, tapi CI merah = jaring pengaman mati.

### 2.2 Pembayaran tunai tidak pernah masuk database
`App/src/components/OrderView.tsx:77` — `chooseCash()` hanya menulis `localStorage`.
Tidak ada panggilan API, tidak ada server action.

Akibat di sisi kafe:
- Kolom `payment_method` tetap `null` untuk **semua** pesanan tunai.
- `ExportReport.tsx:77` menampilkan `-` di kolom Metode.
- Laporan penjualan tidak bisa memisahkan tunai vs QRIS.
- Tidak ada cara bagi kasir menandai pesanan tunai sebagai lunas — `payment_status`
  tunai selamanya `unpaid` di database.

Ini bukan bug kosmetik: modul revenue melaporkan angka yang salah.

### 2.3 Tombol "Sudah Bayar" memalsukan status lunas
`App/src/components/OrderView.tsx:112` — `confirmQrisPaid()` menyetel
`payment_status: "paid"` di `localStorage` tanpa memverifikasi apa pun ke server.
Labelnya "Sudah Bayar? Cek Status Manual" (baris 417) — padahal tidak mengecek apa pun.

Tamu bisa menekan tombol itu tanpa membayar dan menunjukkan layar "LUNAS" ke pramusaji.
Database tetap benar, jadi ini bukan kebocoran uang otomatis — tapi jadi vektor penipuan
sosial di lantai kafe.

Perbaikan: ubah jadi polling ke endpoint `GET /api/orders/[id]?token=…` yang membaca
`payment_status` sebenarnya dari database.

### 2.4 Realtime pembayaran kemungkinan mati
`OrderView.tsx:55` berlangganan `postgres_changes` di tabel `Orders` memakai klien anon.
Tapi `migrations/2026-07-14_security_and_performance.sql` menjalankan
`revoke all on table public."Orders" from anon`.

Supabase Realtime menghormati RLS — tanpa hak select, event UPDATE tidak akan terkirim
ke anon. Artinya konfirmasi QRIS otomatis diam-diam tidak jalan, dan itu menjelaskan
kenapa tombol manual di 2.3 ada.

**Perlu diverifikasi langsung di staging** sebelum diperlakukan sebagai bug pasti —
saya membaca kode dan migrasi, bukan menjalankan sesi Realtime.

### 2.5 Order hilang kalau storage dibersihkan
`App/src/lib/orders.ts` menyimpan seluruh order hanya di `localStorage`. Tidak ada
fallback ambil-dari-server. Konsekuensi:

- Refresh di mode incognito → layar "pesanan tidak ditemukan".
- Ganti HP / bagikan link ke teman semeja → tidak bisa dibuka.
- Bersihkan cache browser → riwayat pesanan lenyap.

Kolom `customer_token` sudah ada di database dan sudah dipakai `charge/route.ts` sebagai
kredensial. Tinggal dipakai untuk pengambilan order berbasis server.

### 2.6 Kuota AI tidak dibatasi — lubang biaya
Enam route AI (`api/tripo/*`, `api/menu/extract`, `api/menu/generate-details`) semua
sudah digate `getAuthCafeId()` — bagus. Tapi tidak ada satu pun yang mengecek kuota.

`STRATEGY.md` §4 menyebut biaya generate ~$0.2–0.6 per model dan menyatakan
"wajib dibatasi credit per tier". `SubscriptionType` ada di `types/index.ts:1` tapi
tidak pernah dibaca di mana pun kecuali sebagai deklarasi tipe.

Satu kafe Tier 50k bisa membakar generate tanpa batas. Pada 10 kafe pilot ini masih
bisa dipantau manual; pada 50 kafe ini kerugian yang tak terkendali.

### 2.7 `status_lunas` hanya menggerbangi menu publik
`supabase.ts:20` memfilter `status_lunas = true` di `getCafeBySlug` — jadi menu publik
mati saat langganan lewat jatuh tempo. Benar.

Tapi dashboard tidak mengecek `status_lunas` sama sekali. Kafe yang menunggak tetap bisa
masuk, mengedit menu, dan membakar credit AI. Gerbang bayar harus juga menutup dashboard —
minimal route AI-nya.

## 3. Temuan — Sebaiknya Diperbaiki

- **Menu nonaktif bocor lewat API.** `getMenusByCafeId` mengambil semua baris lalu
  memfilter `isMenuAvailableNow()` **di klien**. Menu nonaktif dan menu di luar jadwal
  tetap terkirim ke browser lengkap dengan harga. Filter jadwal sebaiknya pindah ke query.
- **`Analytics_Logs` bisa di-insert anon tanpa batas.** `logEvent` menulis lewat klien
  anon tanpa rate-limit. Siapa pun bisa mengembungkan angka analytics kafe. Sudah ada
  migrasi retensi (`20260724120001`) yang meredam biaya penyimpanan, tapi integritas data
  tetap tak terlindungi.
- **Dua direktori migrasi.** `App/migrations/` (6 file, penamaan `2026-07-23_*`) dan
  `App/supabase/migrations/` (2 file, penamaan timestamp Supabase). Tidak jelas mana yang
  otoritatif atau bagaimana urutannya diterapkan. Satukan.
- **RLS untuk `Cafes`, `Menus`, `Announcements`, `Analytics_Logs` tidak ada di repo.**
  Kalau diterapkan lewat konsol Supabase, kebijakan itu tidak ter-version-control dan
  tidak bisa direproduksi di lingkungan baru.
- **Webhook Midtrans tidak idempoten terhadap notifikasi ulang.** Guard
  `.eq("payment_status", "pending")` sudah menangani double-settlement, tapi
  `transaction_status` selain settlement/capture (expire, cancel, deny) diabaikan diam-diam —
  order tersangkut di `pending` selamanya dan stok yang sudah dipotong tidak dikembalikan.
- **Dua worktree sudah merged** (`codex/platform-hardening`, `feature/inventory-core`)
  masih menempel. 7 branch dependabot menumpuk belum di-review.

## 4. Yang Sudah Bagus

- **Server Actions konsisten cafe-scoped.** Setiap mutasi memanggil `getAuthCafeId()` lalu
  menambahkan `.eq("cafe_id", cafeId)` di query. Pola ini menutup IDOR secara sistematis,
  bukan per-kasus.
- **Pembuatan order atomik.** `create_order_with_inventory` RPC menyatukan validasi menu,
  potong stok, dan insert order dalam satu transaksi `security definer` — mencegah stok
  minus akibat race.
- **Rate limiter fail-open dengan alasan tertulis.** `rate-limit.ts` memilih meloloskan
  trafik saat limiter rusak, dan komentarnya menjelaskan kenapa (menolak pesanan pelanggan
  lebih merugikan kafe). Trade-off yang disengaja dan didokumentasikan.
- **Claim atomik sebelum charge Midtrans.** `charge/route.ts:45` menandai `pending` dengan
  guard `.eq("payment_status", "unpaid")` sebelum memanggil Midtrans, dan mengembalikan
  ke `unpaid` kalau Midtrans menolak. TOCTOU double-charge tertutup rapi.
- **Test menyasar risiko nyata**, bukan cakupan kosmetik: SSRF, CSV injection, escaping HTML,
  auth route AI, race inventory.

## 5. Drift Strategi

`STRATEGY.md` §1 menyatakan tegas: *"3Diner = lapisan pengalaman + marketing untuk cafe,
BUKAN POS… Tanpa kasir, tanpa KDS, tanpa payment in-app."*
`MVP-SCOPE.md` §5 menaruh ordering in-app, payment in-app, dan KDS di daftar YAGNI.

Yang sebenarnya terbangun: keranjang, order in-app, QRIS Midtrans, dashboard order dengan
realtime (KDS de-facto), inventory dengan resep dan potong stok otomatis, laporan penjualan.

**Itu POS.** Bukan berarti salah — sinyal dari pilot mungkin memang menuntutnya. Tapi dua
dokumen keputusan itu sekarang menyesatkan siapa pun yang membacanya, dan penentuan tier
(§5: dish 3D aktif + AI credit) tidak mencerminkan bahwa modul termahal untuk dioperasikan
sekarang justru pembayaran dan inventory. Perbarui dokumennya, atau putuskan sadar untuk
memangkas kembali.

## 6. Rekomendasi Fitur

### Prioritas 1 — Menutup yang setengah jadi

**A. Sinkronisasi status pembayaran end-to-end** (§2.2–2.5)
- `GET /api/orders/[id]?token=…` → order dari server, bukan localStorage.
- `POST /api/orders/[id]/payment` → catat pilihan tunai ke database.
- Tombol "Tandai Lunas" di dashboard order untuk pembayaran tunai — kasir sebagai otoritas,
  bukan tamu.
- Ganti tombol palsu "Sudah Bayar" dengan polling status sungguhan.

Tanpa ini, modul revenue melaporkan angka yang salah dan tidak ada satu pun laporan
keuangan yang bisa dipercaya.

**B. Metering credit AI per tier** (§2.6)
- Kolom `ai_credits_quota` + `ai_credits_used` di `Cafes` (sudah disebut sebagai kebutuhan
  di `MVP-SCOPE.md` §2, belum dibuat).
- Cek kuota di semua route Tripo + Gemini, kembalikan 402 saat habis.
- Meteran sisa credit di dashboard.
- Gate `status_lunas` di route AI.

Ini yang mengubah 3Diner dari proyek dengan biaya variabel tak terbatas menjadi SaaS
dengan margin yang bisa dihitung.

**C. Varian & add-on menu**
`CartItem` hanya punya `id_menu`, `nama_menu`, `harga_menu`, `qty`. Tidak ada ukuran,
tingkat gula, level es, extra shot, topping. Hampir tidak ada kafe sungguhan yang menunya
sesederhana itu — tanpa ini, kolom "catatan" bebas jadi tempat pembuangan, dan potong stok
otomatis salah hitung karena resep tidak tahu variannya.

Perlu `Menu_Options` + `Menu_Option_Values`, dikaitkan ke `Menu_Recipes` agar
pemotongan stok akurat per varian.

### Prioritas 2 — Menguatkan hook UGC

**D. Tangkap & bagikan foto AR** — ini yang langsung melayani pitch di `STRATEGY.md` §3
("pelanggan foto, share, cafe rame sendiri"). AR sudah jalan; yang belum ada tombol
shutter. Tambahkan capture kanvas WebXR → overlay logo kafe → Web Share API.
Tiap share = iklan gratis, dan jadi metrik yang bisa ditagihkan ke kafe
("bulan ini 240 foto AR dibagikan").

**E. Panggil pramusaji** — tombol di halaman menu → notifikasi realtime ke dashboard.
Infrastruktur realtime dan channel per-kafe sudah ada, tinggal dipakai. Biaya bangun
rendah, nilai harian tinggi buat kafe.

**F. Ajakan review Google setelah pesanan siap** — `google_maps_review_url` sudah ada di
`Cafes` dan sudah tampil di halaman menu, tapi tidak pernah muncul di layar "pesanan siap" —
persis momen kepuasan tertinggi. Pindahkan/duplikasikan ke sana.

### Prioritas 3 — Nilai jangka panjang

**G. Rekomendasi "sering dipesan bareng"** — data order sudah terkumpul dan belum
dimanfaatkan sama sekali. Query co-occurrence sederhana di `Orders.items` sudah cukup untuk
upsell di keranjang. Efek langsung ke AOV, dengan biaya nol tambahan.

**H. Bilingual ID/EN** — semua string di-hardcode bahasa Indonesia. Untuk kafe yang
menyasar turis/mahasiswa asing, ini penghalang. Butuh refactor menyeluruh, jadi makin murah
kalau dikerjakan sekarang daripada nanti.

**I. Panel super-admin** — `MVP-SCOPE.md` §3b menjanjikannya (onboard kafe, set tier,
toggle `status_lunas`) tapi tidak ada di codebase. Sekarang onboarding pasti manual lewat
konsol Supabase. Pada 20+ kafe ini jadi hambatan operasional.

**J. Loyalitas berbasis `customer_token`** — token sudah unik per order. Kaitkan ke nomor
HP dan ada dasar untuk kartu stempel digital. Sesuai posisi "marketing layer", bukan POS.

### Sengaja tidak direkomendasikan

- **Integrasi POS penuh (ESB/Majoo/Olsera)** — `STRATEGY.md` §1 menolak bersaing di sini,
  dan alasannya masih kuat.
- **Multi-cabang / multi-outlet** — belum ada sinyal permintaan dari pilot Lampung.
- **Aplikasi native** — PWA sudah terpasang (`@ducanh2912/next-pwa`) dan AR jalan di
  browser. App native menambah biaya distribusi tanpa kemampuan baru.
