## Risiko hilang diam-diam

1. **Guard sesi + redirect ke /login** — Saat rebuild sering orang memindahkan fetching ke client component; redirect server hilang dan halaman jadi flash kosong / bocor shell dashboard ke user anonim.
2. **Query pesanan ter-scope kafe: 60 terbaru, urut menurun** — Batas 60 dan urutan desc mudah hilang saat query dipindah/di-refactor; akibatnya halaman jadi berat atau pesanan baru muncul di bawah. Guard cafe_id kalau hilang = kebocoran lintas tenant.
3. **Dedupe lookup auth+kafe lewat React cache()** — Kalau rebuild memanggil supabase.auth.getUser() langsung di page, jumlah round-trip auth berlipat dan halaman terasa lambat tanpa ada error yang terlihat.
4. **Header halaman + animasi reveal** — Subjudul "diperbarui otomatis" adalah satu-satunya penjelasan bahwa halaman ini realtime; gampang dibuang saat header dirapikan. Lebar maksimal 1100px juga sering hilang jadi konten melar di monitor lebar.
5. **Skeleton loading khusus route (shimmer)** — File loading.tsx terpisah dari komponen; rebuild yang fokus di OrdersClient.tsx sering lupa menyesuaikannya, sehingga skeleton jadi tidak cocok dengan layout baru (layout shift) atau terhapus diam-diam.
6. **Tab filter status: Semua / Baru / Diproses / Siap** — Mudah diganti Select/dropdown saat rebuild; padahal chip di sini adalah alat kerja dapur (satu ketukan). Nilai filter juga harus tetap bertahan saat realtime memutakhirkan state orders.
7. **Penghitung angka per tab dihitung dari seluruh data, bukan hasil filter** — Sangat mudah salah di-rebuild jadi menghitung dari `shown` (data yang sudah difilter), yang membuat semua tab non-aktif menampilkan 0. Bug ini tidak melempar error, jadi lolos review.
8. **Baris tab bisa digulir horizontal tanpa scrollbar** — flex-wrap sering dipakai sebagai "perbaikan" saat rebuild, membuat toolbar jadi 2 baris di HP dan mendorong kartu ke bawah. Class no-scrollbar juga sering hilang saat komponen dipindah.
9. **Toggle alarm pesanan (Alarm Aktif / Alarm Mati)** — Tooltip lewat atribut `title` sangat mudah hilang bila tombol diganti komponen Button shadcn. Perilaku "label hilang di mobile, ikon tetap" juga sering jadi label yang memaksa toolbar melebar.
10. **Preferensi alarm bertahan di localStorage ("3diner.orderAlerts")** — Kunci string persis "3diner.orderAlerts" mudah berubah saat rebuild (kasir kehilangan preferensinya). Pembungkus rAF juga sering dibuang, memunculkan hydration warning atau setState sinkron.
11. **Chime dua nada via Web Audio API (G5 -> C6)** — Ini bukan file .mp3, jadi tidak muncul di daftar aset dan sangat mudah dianggap tidak ada saat rebuild. Frekuensi, jeda 0.13s, dan envelope adalah bagian dari identitas suara; membuat ulang sembarangan mengubah pengalaman dapur. Membuat AudioContext baru setiap bunyi akan menabrak batas browser.
12. **Priming audio di dalam gesture pengguna** — Terlihat seperti "bunyi sample yang tidak perlu" dan sering dihapus. Jika playChime dipindah ke useEffect setelah state berubah, konteks gesture hilang dan alarm jadi bisu diam-diam di Chrome.
13. **Permintaan izin notifikasi browser hanya saat status "default"** — Sangat mudah jadi requestPermission() tanpa syarat saat rebuild, yang menghasilkan prompt berulang / diblokir permanen browser. Guard `typeof Notification !== "undefined"` juga wajib, tanpa itu halaman crash di browser tanpa Notification API.
14. **Notifikasi browser pesanan baru dengan tag anti-tumpuk** — Perbedaan "jumlah item" vs "jumlah baris" halus dan gampang salah di-rebuild. Properti `tag` tidak terlihat di UI sehingga sering hilang, akibatnya notifikasi duplikat menumpuk di pusat notifikasi OS.
15. **Toast pesanan baru kustom dengan dedupe id = ID pesanan** — Opsi `id` adalah kontrak dedupe yang sudah ditutup tes; kalau rebuild memakai toast.success biasa, dedupe hilang dan layar dapur banjir toast identik. Tombol X dengan aria-label "Tutup notifikasi pesanan" juga wajib ada.
16. **Toast peringatan koneksi realtime putus & tersambung kembali (id tetap)** — Ini satu-satunya sinyal bagi kasir bahwa layar sudah basi. Tidak terlihat di kondisi normal, jadi hampir pasti terlupakan saat rebuild. Flag hadIssue juga penting: tanpa itu, toast "tersambung kembali" muncul saat halaman pertama dibuka.
17. **Channel realtime Supabase per kafe dengan filter server-side** — Nama channel dan string filter mudah salah ketik saat disalin ulang; hasilnya langganan diam-diam tidak menerima apa pun (tidak ada error, halaman cuma jadi statis). Menghapus filter berarti setiap kafe menerima event kafe lain.
18. **Dedupe INSERT realtime berdasarkan id_order** — Pola "efek samping di dalam updater setState" tidak lazim dan sering dipindah keluar saat rebuild. Kalau dipindah, dedupe alarm hilang dan reconnect Supabase akan membunyikan alarm untuk pesanan lama.
19. **Merge parsial pada UPDATE realtime** — Gampang di-rebuild jadi `o.id_order === row.id_order ? row : o` yang terlihat lebih bersih tapi membuat item pesanan lenyap saat update parsial datang.
20. **Penghapusan baris pada DELETE realtime** — Cabang DELETE jarang terpakai sehari-hari, jadi hampir pasti tidak diuji saat rebuild. Membaca payload.new (yang null saat DELETE) tidak error tetapi membuat penghapusan tidak berefek.
21. **Ref mirror agar closure langganan selalu memakai handler terbaru** — Kalau rebuild menaruh alertsOn/fireAlert ke dependency array effect, channel Supabase di-unsubscribe & subscribe ulang setiap toggle — memicu badai reconnect dan berpotensi alarm untuk pesanan lama.
22. **Guard disposed + removeChannel saat unmount** — Cleanup diam-diam ini tidak menghasilkan gejala saat pengembangan normal; kalau hilang, dashboard menumpuk channel setiap navigasi dan toast realtime bocor ke halaman lain.
23. **Grid kartu responsif 1 / 2 kolom** — Sering diubah jadi 3 kolom saat rebuild demi "padat", padahal kartu pesanan berisi daftar item panjang dan jadi terlalu sempit di laptop kasir.
24. **Kartu pesanan = DashboardPanel dengan head band, hover lift, dan reveal** — Struktur `<section>` + head band adalah bahasa desain sistem dashboard yang dipakai lintas halaman; kalau kartu Pesanan dibangun ulang sebagai `<div>` biasa, tes pecah dan konsistensi visual lintas halaman hilang. Guard @media (hover:hover) sering dilupakan.
25. **Judul kartu: nomor meja + ID pesanan lengkap** — normal-case/tracking-normal adalah penawar khusus terhadap style uppercase head band; jika hilang, ID pesanan tercetak huruf kapital dan tidak cocok lagi untuk dicocokkan manual dengan database.
26. **Salin ID pesanan dengan umpan balik centang 1,5 detik** — Durasi 1500ms, warna emerald, dan aria-label mudah hilang. Efek group-hover pada ikon adalah detail halus yang biasanya tidak diperhatikan saat menulis ulang markup.
27. **Waktu relatif berbahasa Indonesia (relTime)** — Nilainya dihitung sekali saat render, tidak ada timer — tapi singkatan "mnt" dan pembulatan Math.round mudah berubah jadi format lain (mis. date-fns "about 2 hours ago" berbahasa Inggris) saat rebuild.
28. **Daftar item pesanan dengan varian dan subtotal per baris** — Baris varian hanya muncul untuk pesanan bervarian, jadi mudah tidak pernah terlihat saat pengujian rebuild dan hilang tanpa disadari — padahal dapur butuhnya untuk menyiapkan pesanan dengan benar. Pemisah " · " juga bagian dari bahasa visual.
29. **Pengaman items yang bukan array** — Guard defensif tanpa gejala di data sehat; sangat mudah dianggap kode berlebih dan dibuang, lalu satu baris jsonb rusak menjatuhkan seluruh halaman pesanan.
30. **Baris pembayaran (PaymentRow): label metode + pil status lunas** — Kondisi "Metode belum dipilih" hanya muncul untuk pesanan lama/anomali dan hampir pasti terlewat saat rebuild, sehingga jatuh ke label kosong atau "undefined".
31. **Tombol "Tandai Lunas" hanya untuk pesanan tunai / metode belum dipilih** — Aturan bisnis ini hidup di dua tempat (UI dan RPC). Kalau rebuild menampilkan tombol untuk QRIS, server tetap menolak dengan pesan error — jadi UI-nya menipu kasir. Ini kelas bug yang tidak akan tertangkap oleh smoke test.
32. **Pelunasan tunai TIDAK optimistis (menunggu konfirmasi database)** — Perbedaan sengaja antara markPaid (pesimistis) dan advance (optimistis) tidak akan terbaca oleh siapa pun yang menulis ulang; menyeragamkannya jadi optimistis akan membuat uang tercatat lunas di layar padahal database menolak.
33. **Server action markOrderCashPaid: guard tenant, RPC, dan revalidate ganda** — revalidatePath("/dashboard/revenue") mudah hilang karena tidak berdampak apa pun di halaman Pesanan sendiri; akibatnya laporan penjualan menampilkan angka basi sampai user hard refresh.
34. **Blok catatan pesanan pelanggan** — pre-wrap adalah satu-satunya penjaga format catatan; hilang berarti instruksi pelanggan menempel jadi satu kalimat. Blok ini juga tidak muncul di kebanyakan pesanan uji.
35. **Baris total + tombol majukan status (Mulai Proses / Tandai Siap)** — Tiga varian warna + ikon + teks + kondisi terminal ini adalah alur kerja dapur. Rebuild yang menyederhanakannya jadi satu tombol "Next" secara teknis tetap jalan tapi menghapus makna yang dipakai staf.
36. **Optimistic update pada perubahan status pesanan** — Kalau rebuild memakai pola await-lalu-setState, dapur akan merasakan jeda 1-2 detik tiap ketukan. Perlu dicatat juga bahwa perilaku saat ini memang tidak memberi toast bila server gagal — kalau rebuild menambahkannya, itu perubahan perilaku yang harus disengaja.
37. **Server action updateOrderStatus: guard kafe + revalidatePath** — Filter cafe_id kedua adalah penjaga multi-tenant yang tidak kelihatan di UI sama sekali; sangat mudah tersisa hanya .eq("id_order") saat kode disalin ulang.
38. **Badge status memakai vocabulary StatusBadge sistem** — Kalau kartu Pesanan membuat badge sendiri saat rebuild, label bisa menyimpang dari halaman Penjualan/Inventori yang memakai kind yang sama, dan titik indikator (aksesibilitas buta warna) mudah dibuang.
39. **Tombol preview & cetak struk pada head band kartu** — Menyimpan event.currentTarget saat klik terlihat seperti detail sepele dan biasanya hilang; tanpa itu, pemulihan fokus setelah modal ditutup ikut mati (lihat fitur restore focus / baris 48).
40. **Modal struk dirender ke dashboard portal root (aturan token portal)** — Kalau container dilepas saat rebuild, dialog mendarat di body dan kehilangan variabel --dash-* sehingga warnanya berubah jadi tema terang. Ini sudah dikunci tes tetapi hanya untuk halaman ini.
41. **Pratinjau struk di dalam iframe dengan tinggi menyesuaikan isi** — Pengukuran tinggi otomatis di onLoad adalah trik satu baris yang mudah hilang; hasilnya struk terpotong pada 420px tanpa cara menggulir karena scrolling="no".
42. **Detail visual kertas: perforasi atas dan bawah** — Murni dekoratif, jadi hampir pasti dipangkas saat rebuild demi "kebersihan" — padahal ini yang membuat pratinjau terbaca sebagai struk, bukan sekadar teks.
43. **Header dan aksi modal struk (Tutup / Cetak Sekarang)** — Urutan "cetak lalu tutup" penting; kalau dibalik atau modal dibiarkan terbuka, kasir harus dua kali menutup. aria-label pada X sudah dipakai tes, jadi harus dipertahankan persis.
44. **Perakit HTML struk termal 80mm (buildReceiptHtml)** — Fungsi ini di-ekspor dan diuji terpisah; kalau rebuild memindahkannya ke dalam komponen atau mengganti pendekatan ke react-to-print, empat tes escaping langsung pecah. Angka 80mm, 32 karakter, dan @page margin 0 adalah kalibrasi printer termal nyata — bukan angka acak.
45. **Escaping HTML wajib untuk semua teks asal publik pada struk** — table_number dan notes datang dari POST /api/orders yang publik tanpa auth. Rebuild yang beralih ke template literal biasa atau dangerouslySetInnerHTML membuka XSS pada halaman dashboard pemilik. Ini risiko keamanan, bukan kosmetik.
46. **Format tanggal dan waktu id-ID pada struk** — Kalau rebuild mengganti ke format ISO atau locale en-US, struk pelanggan berubah jadi "07/21/2026 10:00 AM". Perbedaan sengaja antara toLocaleString polos (struk) dan formatRupiah (layar) juga mudah diseragamkan keliru sehingga "Rp" tercetak dua kali.
47. **triggerPrint: cetak lewat iframe tersembunyi dengan timing terkalibrasi** — Jeda 350ms dan pembersihan 1500ms adalah hasil kalibrasi; window.print() langsung akan mencetak halaman dashboard, bukan struk. Kebocoran iframe tidak terlihat sampai kasir mencetak puluhan kali dalam satu shift.
48. **Pemulihan fokus keyboard setelah modal struk ditutup** — Perilaku aksesibilitas yang tidak terlihat sama sekali oleh pengguna mouse; hampir pasti hilang saat rebuild dan hanya ketahuan lewat tes yang sudah ada. Ref-nya bergantung pada event.currentTarget yang disimpan saat klik.
49. **Empty state dengan CTA "Bagikan QR Menu"** — Empty state versi filter jarang terpikirkan (biasanya hanya diuji untuk kondisi 'tidak ada data sama sekali'). Anchor #qr-menu mudah putus kalau id di halaman Pengaturan ikut berubah, dan CTA sering diganti teks pasif tanpa aksi.
50. **Format Rupiah dan angka tabular di seluruh area** — tabular-nums adalah detail tipografi yang selalu hilang saat markup ditulis ulang, dan gejalanya (angka bergetar saat update realtime) mudah dianggap wajar. Locale id-ID juga sering jatuh ke default browser.
51. **Lapisan mikro-interaksi dashboard (dash-btn, dash-press, dash-chip)** — Class-class ini terlihat seperti sisa dan sering diganti utilitas Tailwind generik saat rebuild, sehingga seluruh dashboard kehilangan rasa tekan yang konsisten antar halaman.
52. **Penghormatan prefers-reduced-motion dan cincin fokus keyboard** — Aturan reduced motion khusus untuk .dash-reveal bersifat penyelamat — kalau nama class berubah saat rebuild tetapi CSS-nya tidak, pengguna reduce motion akan melihat kartu yang tidak pernah muncul (opacity 0 permanen). Cincin fokus juga sering dimatikan demi estetika.
53. **Toaster Sonner ditempatkan di dalam .dash-root, posisi top-right** — Berada di file layout yang berbeda dari area ini, jadi rebuild OrdersClient bisa mengasumsikan posisi/tema toast lain. Kalau Toaster dipindah ke root layout, semua toast Pesanan kehilangan token dashboard dan berubah jadi tema terang.
